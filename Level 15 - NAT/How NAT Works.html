🌐 NAT — What & Why

Network Address Translation (NAT) rewrites the addresses (and sometimes ports) in a packet as it crosses a router boundary — most commonly an inside (private) network reaching the outside (public) Internet.

NAT changes addresses — it does not repair routing, override security policy, or magically make something reachable. Reachability, routing, return path, and security must all still be correct.

📌 Static NAT — permanent 1:1

A manual, permanent one-to-one mapping between an Inside Local address and an Inside Global address. It exists in the table even with no traffic.

The 1:1 mapping

ip nat inside source static 192.168.10.100  203.0.113.100
   loadJSONs LOCAL      inside GLOBAL

Inside Local       Inside Global
192.168.10.100  ↔  203.0.113.100
Trap: static NAT being present does not automatically make the server reachable from outside. It still needs a route, reachability, a working return path, and a permissive security policy.

Key idea: static NAT is bidirectional — a permanent entry exists both ways, so unsolicited inbound connections to the mapped public address are possible (unlike dynamic NAT).

♻️ Dynamic NAT — temporary 1:1 pool

Dynamic NAT draws from a pool of public addresses. A mapping is created only when eligible traffic needs it, stays while the session is active, and ages out — returning the address to the pool.

ip nat pool PUBLIC 203.0.113.10 203.0.113.19 netmask 255.255.255.0
ip nat inside source list 10 pool PUBLIC
access-list 10 permit 192.168.10.0 0.0.0.255
Important: dynamic NAT does not translate TCP/UDP ports. It is 1:1 — each inside host needs its own pool address. An outside host cannot initiate a new connection to an inside host (no permanent mapping exists).

🔌 PAT (NAT Overload) — many inside hosts, few public IPs

Port Address Translation lets many inside hosts share one (or a few) public IP by using distinct Layer-4 TCP/UDP source ports to keep flows unique.

! share the interface's public IP
ip nat inside source list 10 interface GigabitEthernet0/1 overload
access-list 10 permit 192.168.0.0 0.0.255.255

Uniqueness: PAT works because each flow maps to a distinct (public IP, source port) combination. If two hosts coincidentally use the same source port to the same destination, IOS translates one of them to a different port.
Not immune: do not describe PAT as "unlimited". PAT can exhaust available translation (port) resources under load.

🧭 Policy NAT — conditional translation

Policy NAT answers "which traffic is translated, and how" — based not just on the inside source, but on destination, protocol/ports, and a route-map.

A regular source NAT matches only the inside source via an ACL (ip nat inside source list ...). Policy NAT matches more, and can map different traffic to different public addresses.

! traffic to ISP-A → translated with ISP-A's address
ip nat inside source route-map ISP-A pool PUB-A
ip nat pool PUB-A 203.0.113.10 203.0.113.10 netmask 255.255.255.0
route-map ISP-A permit 10
 match ip address 100
 match ip next-hop 10.0.0.254

! traffic to ISP-B → translated with ISP-B's address
ip nat inside source route-map ISP-B pool PUB-B
ip nat pool PUB-B 198.51.100.10 198.51.100.10 netmask 255.255.255.0
route-map ISP-B permit 10
 match ip address 100
 match ip next-hop 20.0.0.254

🔄 NAT64 + DNS64 — IPv6-only to IPv4-only

NAT64 lets IPv6-only clients talk to IPv4-only servers by translating IPv6 ↔ IPv4. It commonly works with DNS64, which synthesizes an AAAA record so the v6 client knows which IPv6 destination to use.

IPv6 Client → DNS64 → NAT64 → IPv4 Server
synthesizes AAAA translates packets

DNS64 vs NAT64 — different jobs

TechnologyFunction
DNS64synthesizes IPv6 AAAA records from IPv4 A records (changes the DNS answer only)
NAT64translates IPv6 packets into IPv4 packets and back
Trap: DNS64 is not NAT64. They are complementary: DNS64 picks the IPv6 destination; NAT64 translates the resulting traffic.

🔧 NAT Troubleshooting

A structured path: Interface classification → Rule matching → Translation creation → Forwarding → Return traffic → Application behavior.

Where the packet stops

1 enters NAT inside interface?
2 does the NAT rule/ACL match?
3 can a translation be created?
4 forwarded toward the outside?
5 does return traffic reach the NAT?
6 is return traffic reverse-translated?

Symptom → cause → verify

SymptomLikely causeVerify with
Nothing translatesWrong inside/outside classificationshow ip nat statistics
No hosts translatedACL does not matchshow access-lists
Dynamic NAT fails for new hostsPool exhaustionshow ip nat statistics
Outbound works, reply failsReturn-path / routing problemshow ip route
Unsolicited inbound failsMissing static NAT/PAT or filteringNAT config + ACL
Ping works, app failsPort/protocol/application issueapp test + NAT state

Inbound: return vs unsolicited

Return for an existing session

Inside host initiated the flow. Return traffic uses the existing dynamic NAT/PAT state. No additional static mapping needed just because the packet is inbound.

Unsolicited inbound

An outside host initiates toward an inside server. This normally requires a static NAT or static PAT mapping (plus routing + security policy).

! static PAT example — outside client reaches inside server:443
ip nat inside source static tcp 192.168.10.100 443 203.0.113.100 443
Trap: "No ICMP translation because ICMP can't be translated" is wrong. IOS NAT can translate ICMP using its identifier to distinguish sessions. If ICMP isn't translating, check classification/ACL/routing/state — not "ICMP can't translate".
Mindset: NAT does not replace routing. Both forward and return paths must be correct. Don't blame an ALG for every app failure — verify NAT state, routing, ports, and protocol first.
