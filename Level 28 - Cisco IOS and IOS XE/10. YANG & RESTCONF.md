# YANG & RESTCONF on IOS XE

> **Level 28 · Cisco IOS and IOS XE** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**YANG** is a **data-modeling language** that describes device configuration/state as a
structured tree, and **RESTCONF** plus **NETCONF** are the model-driven protocols that
read/write that model over a network. On IOS XE they enable **programmatic, model-driven
configuration and telemetry** instead of screen-scraping the CLI. The exam tests YANG's
purpose, RESTCONF vs NETCONF differences, and enabling them on IOS XE.

---

## 2. Core Concepts

### 2.1 What YANG is

| Item | Detail |
|------|--------|
| Type | data-modeling language (RFC 6020/7950) |
| Purpose | describe configuration + operational state |
| Form | structured tree of nodes |
| Vendor | Cisco native + OpenConfig models |
| Use | NETCONF/RESTCONF/gNMI |

- **YANG defines the data model** (what a network looks like); NETCONF/RESTCONF move that
  data.

### 2.2 NETCONF vs RESTCONF

| Aspect | NETCONF | RESTCONF |
|--------|---------|----------|
| Transport | **SSH (port 830)** | **HTTPS (port 443)** |
| Payload | XML | JSON/XML |
| API style | RPC (operations) | RESTful (GET/POST/PUT/DELETE) |
| Standard | RFC 6241 | RFC 8040 |
| Push/notifications | yes (nc-notify) | less native |
| Use | change mgmt, streaming | simple web apps |

- **NETCONF = SSH/XML/RPC**; **RESTCONF = HTTPS/JSON/REST**.

### 2.3 How they work on IOS XE

```
Client --YANG model--> device
Device exposes config/state per YANG tree
Client reads/writes via NETCONF (SSH 830) or RESTCONF (HTTPS 443)
```

- The YANG model is the **contract**; NETCONF/RESTCONF are the **verbs** to act on it.

### 2.4 Enabling on IOS XE

```text
! enable RESTCONF
restconf
!
! enable NETCONF
netconf-yang
!
! optional
netconf-yang ssh port 830
ip http secure-server
```

| Command | Purpose |
|---------|---------|
| `restconf` | enable RESTCONF (HTTPS 443) |
| `netconf-yang` | enable NETCONF (SSH 830) |
| `ip http secure-server` | HTTPS support for RESTCONF |

### 2.5 YANG data models

| Model | Source |
|-------|--------|
| **Cisco-IOS-XE-native** | maps to native CLI |
| OpenConfig | vendor-neutral |
| IETF models | standard |
| YANG modules | contain containers/lists/leafs |

- The **native model mirrors the CLI**; OpenConfig is cross-vendor.

### 2.6 Typical operations

| Operation | RESTCONF | NETCONF |
|-----------|----------|---------|
| Read config/state | GET | get / get-config |
| Create/update | PUT/POST/PATCH | edit-config |
| Delete | DELETE | edit-config (delete) |
| Subscribe telemetry | — | subscribe (RFC) |
| Datastore | running/candidate | running, candidate |

## 5. Exam Traps

- **YANG is the model; NETCONF/RESTCONF are the protocols** — don't conflate them.
- **NETCONF = SSH (830) + XML + RPC**; **RESTCONF = HTTPS (443) + JSON/XML + REST**.
- Enable with **`restconf`** and **`netconf-yang`**.
- The **native YANG model mirrors the CLI**.
- Model-driven management is the enabler for **SDN automation and telemetry**.

## 7. One-Minute Mental Model

Think **YANG = the blueprint, NETCONF/RESTCONF = the delivery trucks**. YANG defines the
device's config/state as a structured tree (the native Cisco model mirrors the CLI, with
OpenConfig for multi-vendor). **NETCONF** hauls it over **SSH 830 in XML via RPC**;
**RESTCONF** uses **HTTPS 443 with JSON via REST** (GET/PUT/POST/DELETE). Enable both with
`restconf` and `netconf-yang`, and you've opened IOS XE to scripting, SDN, and streaming
telemetry.
