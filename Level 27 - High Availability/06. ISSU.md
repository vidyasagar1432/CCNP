# ISSU (In-Service Software Upgrade)

> **Level 27 · High Availability** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**ISSU (In-Service Software Upgrade)** lets you upgrade the IOS XE software on a **dual
supervisor** device **without taking the network down**. It uses **SSO** (stateful
switchover, note 01) and an **NSF-aware** routing stack: upgrade the standby, **switch over
control** to it, then upgrade the old active — all with minimal or zero traffic loss. The
exam tests the ISSU stages and why it needs SSO + NSF.

---

## 2. Core Concepts

### 2.1 What ISSU requires

| Requirement | Why |
|-------------|-----|
| **Dual supervisors** | one to upgrade while the other runs |
| **SSO** | stateful control-plane sync between them |
| **NSF / graceful restart** | continue forwarding during switchover |
| Compatible images | ISSU is only for **nondisruptive** upgrades |

- ISSU fundamentally depends on **SSO + NSF** being enabled first.

### 2.2 The ISSU process stages

| Stage | Action |
|-------|--------|
| 1 | **Loadnew** — install new image on standby |
| 2 | **Runversion** — standby runs new image (SSO maintained) |
| 3 | **Switchover** — control moves to standby (SSO, no drop) |
| 4 | **Loadold** — load old image on the now-standby (old active) |
| 5 | **Commit** — write new image, complete |

- The sequence is **loadnew → runversion → switchover → loadold → commit**.

### 2.3 The two phases of ISSU

| Phase | Meaning |
|-------|---------|
| **Phase 1 (pre-switchover)** | upgrade the standby |
| **Phase 2 (post-switchover)** | upgrade the old active to match |

- Control **switches over** between the two phases so traffic never stops.

### 2.4 ISSU compatibility

| Aspect | Detail |
|--------|--------|
| Same train / compatible | supported |
| Major version jump | may need full reload instead |
| SMU/subpackage | compatible patches supported |
| Feature set change | check compatibility matrix |

- Not every upgrade is ISSU-capable — **major jumps** may force a reboot.


|---------|---------|
| `install add ... activate` | modern ISSU-like install |
| `show install summary` | installed packages |
| `show issu state` | ISSU progress |
| `show redundancy states` | SSO status |

### 2.6 ISSU vs rollback

| Aspect | ISSU | Full reload upgrade |
|--------|------|---------------------|
| Downtime | near zero | outage |
| Requires | SSO/NSF + dual RP | none |
| Use | enterprise backbone | simple sites |
| Risk | image compatibility | simple |

- ISSU trades **simplicity for zero downtime**; plain reload is simpler but disruptive.

## 4. Troubleshooting & common failures

## 5. Exam Traps

- ISSU requires **dual supervisors + SSO**; it is not available on a single-supervisor box.
- Stages: **loadnew → runversion → switchover → loadold → commit**.
- Zero/near-zero down time because of **SSO switchover + NSF forwarding**.
- **Major image jumps** may not be ISSU-capable (force a reload).
- Verify with **`show issu state`** and `show redundancy states`.

## 7. One-Minute Mental Model

**ISSU** = "upgrade without the outage". Upgrade the **standby** supervisor to the new
image (**loadnew → runversion**), **switch over** control with SSO (no drop, thanks to
NSF), upgrade the old active, and **commit**. Because everything rides on SSO switchover +
graceful restart, ISSU only works on **dual-supervisor, SSO** boxes — and only for
compatible image pairs. If you see a single RP or a major version jump, expect a reload.
