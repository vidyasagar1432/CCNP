# Redundancy Design & Best Practices

> **Level 27 · High Availability** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**Redundancy design** is the disciplined selection of HA mechanisms to match a business
availability target. It layers **device, link, gateway, and path** redundancy and follows
best practices — one failure domain, no single point of failure, fast convergence, and
testing. The exam tests how SSO/NSF, EtherChannel, FHRP, and routing failover fit together
into a coherent design.

---

## 2. Core Concepts

### 2.1 Availability tiers / goals

| Tier | Downtime target | Mechanisms |
|------|-----------------|------------|
| Best effort | none guaranteed | basic |
| High availability | ~99.99% | SSO/NSF, dual paths |
| Always-on | minimal | full stack HA |

- Design **to a target** — not every device needs every mechanism.

### 2.2 The layered redundancy model

| Layer | Mechanism | Protects against |
|-------|-----------|------------------|
| Device/software | SSO, NSF, ISSU (notes 01/02/06) | supervisor/RP failure |
| Chassis | Redundant supervisors (note 03) | brain failure |
| Link | EtherChannel/LAG, M-LAG (note 04) | link/port failure |
| Gateway | HSRP/VRRP/GLBP (note 05) | router/first-hop failure |
| Path | ECMP, routing failover, multihoming | transit/AS failure |
| Power/cooling | PSU/VRD redundancy | facility power loss |

- HA is **layered** — each layer covers a different failure mode.

### 2.3 Best practices

| Practice | Detail |
|----------|--------|
| No SPOF | every critical path has a backup |
| One failure domain | stack/VSS members in same wiring closet |
| Fast convergence | routing/timers tuned (but not too aggressive) |
| Test failovers | scheduled `redundancy force-switchover` |
| Monitor | SNMP/syslog + failure history |
| Same image | consistent IOS/software across peers |
| Symmetric design | input/output redundancy on both sides |

- Best practice 1: **no single point of failure** on any critical path.

### 2.4 Design principles

| Principle | Reason |
|-----------|--------|
| **Redundant ≠ load-shared** | paired devices are usually active/standby |
| **Bundled links** over single channels | EtherChannel avoids STP blocking |
| **Dual-homed** over single-homed | no uplink SPOF |
| **FHRP + routing** together | first-hop + path both covered |
| **Keep states in sync** | via SSO for fast failover |

### 2.5 Common design patterns

| Pattern | Use |
|---------|-----|
| Access: dual-uplink + LAG | server/switch resilience |
| Distribution: VSS/stack + SSO | fast L2 failover |
| Core: ECMP + NSF | routing continuity |
| Edge: FHRP + BGP multihoming | gateway + transit |

---

## 5. Exam Traps

- HA is **layered**: device + link + gateway + path — one mechanism rarely covers everything.
- **Redundant ≠ load-shared**; many designs are active/standby with failover.
- **EtherChannel** beats single links — no STP blocking and cheaper than LAG-less dual.
- **SSO + NSF** is the foundation for zero-loss control failover.
- **Test failover** (`redundancy force-switchover`) — untested redundancy isn't redundancy.

## 7. One-Minute Mental Model

**Redundancy design** = layer the mechanisms so every critical path has a **backup and no
single point of failure**: SSO/NSF for the brain, redundant supervisors for the chassis,
EtherChannel for links, HSRP/VRRP/GLBP for the gateway, and routing/ECMP for paths. Follow
best practices (one failure domain, consistent images, symmetric design, tested failover)
and match the mechanism count to your availability target — not everything needs
everything.
