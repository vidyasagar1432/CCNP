# LLQ & CBWFQ (Low Latency Queuing)

> **Level 21 · QoS** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**[[CBWFQ|CBWFQ (Class-Based Weighted Fair Queuing)]]** is the modern egress scheduling method that
gives each traffic class a **guaranteed bandwidth share**, while **[[LLQ]] (Low Latency
Queuing)** adds a **strict-priority class** (usually voice/EF) served **before** everything
else — but rate-limited to avoid starving other classes. Together they are *the* production
queuing answer for converged voice/video/data. The exam tests `priority` vs `bandwidth` and
the starvation prevention rule.

---

## 2. Core Concepts

### 2.1 CBWFQ model

| Concept | Detail |
|---------|--------|
| Class | matched by class-map |
| Share | `bandwidth` kbps per class |
| Scheduling | packets served proportionally to weight |
| Drop | tail-drop per queue |
| Residual | unused bandwidth redistributed |

- CBWFQ **guarantees each class a configurable share** of the link.

### 2.2 LLQ = strict priority class

| Item | Detail |
|------|--------|
| Command | `priority <kbps>` |
| Behavior | served first, before bandwidth classes |
| Rate-limited | policed to the priority value |
| Use | voice (EF), latency-sensitive |
| Risk | without limit would starve others |

- LLQ = **priority queue + CBWFQ**; the priority class is **policed** so it cannot
  monopolize the link.

### 2.3 priority vs bandwidth (the trap)

| Keyword | Meaning |
|---------|---------|
| `priority` | strict-priority LLQ class, **policed** |
| `bandwidth` | guaranteed weighted share, not strict priority |
| Both | within one policy-map, LLQ first then CBWFQ |

- `priority` = LLQ (strict, policed); `bandwidth` = CBWFQ (guaranteed share, not strict).

### 2.4 Configuration example

```text
policy-map WAN-EDGE
 class VOICE
  priority 128          ! LLQ - strict, policed to 128k
 class VIDEO
  bandwidth 1000        ! CBWFQ guaranteed share
 class DATA
  bandwidth 2000
 class class-default
  fair-queue            ! leftover split fairly
!
interface GigabitEthernet0/1
 service-policy output WAN-EDGE
```

| Command | Meaning |
|---------|---------|
| `priority` | LLQ strict-priority class |
| `bandwidth` | CBWFQ guaranteed share |
| `fair-queue` | per-flow in class-default |
| `queue-limit` | per-class queue depth |

### 2.5 LLQ policing mechanism

- LLQ's priority queue is **rate-limited (policed)** to the configured `priority` value;
  bursts beyond it are dropped — guaranteeing that low-priority classes still get served.


## 4. Troubleshooting & common failures

| Symptom | Likely cause | Check |
|---------|--------------|-------|
| Voice jitter | no LLQ priority class | policy-map |
| Others starved | priority too high | priority value |
| No guarantee | bandwidth not set | policy-map |
| Wrong order | default FIFO | service-policy |
| Queue full | tail drop | queue-limit |

- If **voice jitters** on a congested link, the missing piece is usually an **LLQ
  priority class**.

---

## 5. Exam Traps

- **CBWFQ = per-class guaranteed `bandwidth`**; **LLQ = strict `priority` class**.
- LLQ's priority class **must be policed** to prevent starvation of other classes.
- `priority` (LLQ, policed) vs `bandwidth` (CBWFQ share) — do not confuse them.
- Queuing is **egress**, only matters **under congestion**.
- Voice → **LLQ (EF)**; video/data → **CBWFQ** with proper shares.

## 7. One-Minute Mental Model

**CBWFQ** is the egress scheduler that carves the link into per-class **bandwidth**
shares; **LLQ** is CBWFQ plus a **priority** class served first for delay-sensitive voice
— and it's **policed** so the voice class can't eat the whole link. Use `priority` for
voice (EF), `bandwidth` for video/data. On any congested WAN, that pairing is the
production answer and the exam's favorite queuing question.
