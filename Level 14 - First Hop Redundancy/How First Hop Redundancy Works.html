🛡️ FHRP — What & Why

A First Hop Redundancy Protocol (FHRP) gives hosts a redundant default gateway by sharing a Virtual IP (VIP) + Virtual MAC across multiple routers. Hosts point at one VIP; the FHRP decides which physical device forwards and what happens when it dies.

Hosts → Gateway 10.10.10.1
┌───────────── R1 ─────────────┐
│ ┌─ R2 ──┐ ┌── R3 ──┐ │
└──┴─ Active ┴─── backup ┴─────┘

The core problem FHRPs solve

Without an FHRP

Host
  |
Gateway = 10.10.10.1
  |
Router      ← if this fails,
              hosts lose the gateway

With an FHRP

         ┌── R1 ──┐
Host ──LAN── R2 ──┐── Upstream
         └── R3 ──┘

VIP = 10.10.10.1 (hosts unchanged)
FHRP picks the live router + MAC
Key insight: during a failover the host keeps the same VIP. The FHRP only changes which physical device backs that VIP — no host reconfiguration.
Three facts to remember first: HSRP → Active/Standby · VRRP → Master/Backup · GLBP → AVG/AVF + built-in load balancing.

🔥 Hot Standby Router Protocol (HSRP)

🧩 Virtual Router Redundancy Protocol (VRRP)

Open-standard (IETF) FHRP, built for multi-vendor interoperability. Runs directly over IP protocol 112 (no UDP).

Versions & roles

Versions

  • VRRPv2 — RFC 3768 (IPv4)
  • VRRPv3 — RFC 5798 (IPv4 + IPv6)
Trap: "VRRP = RFC 3768" alone is wrong — that is specifically v2. IPv6 needs v3.

Roles

  • Master — forwards + sends adverts
  • Backup — monitors the Master
  • IP Address Owner — its real IP = VIP → priority 255

States: Initialize → Master / Backup (no Speak/Listen).

⚖️ Gateway Load Balancing Protocol (GLBP)

Cisco-proprietary FHRP with built-in gateway load balancing — multiple routers can actively forward for the same VIP. UDP 3222.

Architecture

AVG — Active Virtual Gateway

One per group. Manages the group, answers ARP for the VIP, assigns virtual MACs to forwarders.

(AVG ≠ the only forwarder.)

AVF — Active Virtual Forwarder

Actually forwards traffic for an assigned virtual MAC. Up to 4 active AVFs per group.

Virtual MAC

Format 0007.b400.XXYY → prefix 0007.b400, group hex, forwarder 01–04.

One VIP → many MACs

🎯 Object Tracking — reacting beyond the local interface

Object tracking lets a feature (HSRP/VRRP/GLBP, a static route, PBR) react to the state of a monitored object — e.g. an upstream interface, a route, or an IP SLA probe — not just whether its own LAN interface is physically up.

Key rule: creating a track object alone changes nothing — the object must be referenced by a consuming feature (e.g. standby 10 track 1 decrement 20).

Tracking & upstream failure — the payoff

Internet → R1 → Clients

If R1's client-facing interface stays UP but the
ISP link fails:
  - without tracking → HSRP still sees R1 healthy → blackhole
  - with IP SLA tracking → SLA fails → track DOWN
      → HSRP priority drops → backup router becomes preferred
Why this matters: object tracking makes failover depend on actual network reachability, not merely "my local interface is up".
