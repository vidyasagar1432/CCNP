# GET VPN

> **Level 18 · VPN Technologies** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

**[[GET VPN|GET VPN (Group Encrypted Transport VPN)]]** provides **any-to-any encryption over an MPLS
or IP backbone without tunnel interfaces**. Instead of building point-to-point tunnels, all
routers in a **group** share a common **group key** and encrypt directly with the **GDOI
(Group Domain of Interpretation)** protocol. There is no hub bottleneck and no overlay
routing — the underlay routes natively. The exam tests GDOI, the key server, and how GET
VPN avoids tunnels.

---

## 2. Core Concepts

### 2.1 The GDOI model

| Role | Description |
|------|-------------|
| **KS (Key Server)** | manages and distributes group keys |
| **Member** | group router, encrypts traffic |
| **Group** | shared key domain |
| **GDOI** | IKEv2/IKEv1-based group key mgmt (UDP 848) |
| **Reg/TEKs** | registration + traffic encryption keys |

- Members register with the **KS** and receive the group key; they encrypt directly
  **peer-to-peer** with the shared key — no tunnel is built between them.

### 2.2 How GET VPN works

```
Member  --register-->  Key Server (GDOI, UDP 848)
KS sends  KEK + TEK (group key)
Member A --encrypt with TEK--> Member B   (direct, no tunnel)
```

- **TEK (Traffic Encryption Key)** encrypts data; **KEK (Key Encryption Key)** protects
  TEK distribution.
- After registration, members share one key and talk **directly** — ideal for hubs that
  don't want their spoke-to-spoke traffic hair-pinned.

### 2.3 Port and transport details

| Item | Detail |
|------|--------|
| GDOI port | UDP 848 |
| IPsec transform | ESP group SA (data) |
| IPsec mode | transport usually |
| Group key | TEK (rekeyed periodically) |
| IKE | used for member↔KS registration |

- GDOI runs on **UDP 848**, separate from normal IKE data-plane tunnels.

### 2.4 GET VPN vs DMVPN / IPsec tunnels

| Aspect | GET VPN | DMVPN | Crypto-map / VTI |
|--------|---------|-------|------------------|
| Tunnel interface | none | mGRE | VTI/GRE |
| Data path | direct (no hub) | spoke-spoke (hub control) | point-to-point |
| Overlay routing | none (native) | NHRP | OSPF/BGP over tunnel |
| Key mgmt | GDOI group key | per-tunnel IKE | per-tunnel IKE |
| Best for | MPLS any-to-any | Internet branch dynamic | fixed sites |
| Rekey | centralized KS | — | — |

- GET VPN's signature is **transport independence + any-to-any** with no tunnels.

### 2.5 GET VPN roles and features

| Feature | Detail |
|---------|--------|
| Any-to-any | full mesh, no hub in data path |
| Backbone | MPLS / any IP network |
| Multicast | supported |
| Registration | member → KS (GDOI) |
| Rekey | KS pushes new TEK/KEK |
| COOP | redundant key servers |
| Anti-replay | via sequence numbers/WAN? |

- **COOP (Cooperative Key Server)** provides redundant KS for high availability.

### 2.6 Configuration snapshot (KS side)

```text
crypto gdoi group ENCRYPT
 identity number 98765
 server local
  rekey
  address ipv4 10.0.0.1
  authorization address ipv4 10.0.0.0 255.255.255.0
!
crypto gdoi server local
```
- Members join via `crypto gdoi group` pointing at the KS.

## 5. Exam Traps

- GET VPN = **group key + GDOI**, **no tunnels** — routers encrypt directly.
- GDOI runs on **UDP 848** (not 500/4500 for data).
- **TEK** encrypts data; **KEK** protects key distribution.
- Best over **MPLS/backbone** where you want native any-to-any without hub hair-pinning.
- **COOP** gives redundant key servers.

## 7. One-Minute Mental Model

**GET VPN** = "IPsec without tunnels." Every group member registers with a **Key Server**
via **GDOI (UDP 848)** and gets a shared **TEK**; members then encrypt to each other
directly, so the MPLS/backbone routes natively and there's never a hub hair-pin or overlay
tree. If the design goal is true any-to-any over a private backbone with zero tunnel
overhead, GET VPN is the answer distinct from DMVPN/VTI.
