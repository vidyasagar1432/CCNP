# Virtual Tunnel Interface (VTI)

> **Level 18 · VPN Technologies** — CCNP Enterprise (ENCOR 350-401)

---

## 1. Overview

A **Virtual Tunnel Interface (VTI)** is a route-based **IPsec tunnel interface** that
carries **IPsec directly over a virtual interface** — no interesting-traffic ACL, no crypto
map. Routing protocols and traffic just transit the VTI, and IPsec policies are bound with
`tunnel protection ipsec profile`. VTI is the modern replacement for crypto-map
policy-based IPsec.

---

## 2. Core Concepts

### 2.1 Route-based vs policy-based IPsec

| Aspect | Policy-based (crypto map) | Route-based (VTI) |
|--------|---------------------------|-------------------|
| What triggers encryption | interesting-traffic ACL | route toward the tunnel |
| Interface | physical/attached crypto map | dedicated virtual tunnel if |
| Routing over it | difficult | natural (OSPF/EIGRP/BGP) |
| Multicast | not directly | yes |
| Config complexity | higher | lower |
| Scale | static peers | dynamic, profile-based |

- VTI decouples **"what to encrypt"** (routing) from **"how to encrypt"** (IPsec profile).

### 2.2 How a VTI works

- `interface Tunnel0` gets an **IP address** and acts as a normal L3 interface.
- IPsec is enabled with **`tunnel protection ipsec profile NAME`**.
- Traffic routed into the tunnel (including **multicast**) is automatically encrypted.
- No need to mirror interesting-traffic ACLs on both ends — **routing is the control**.

### 2.3 VTI vs GRE over IPsec

| Aspect | GRE over IPsec | VTI |
|--------|----------------|-----|
| Overhead | GRE (4 B) + IPsec | direct IPsec (no GRE) |
| Multicast | yes (GRE) | yes |
| Routing | over GRE tunnel | over VTI directly |
| Config | tunnel + GRE + profile | tunnel + profile |
| Encapsulation | IP = GRE = IPsec | IP = IPsec |

- VTI drops the **GRE layer** for a leaner stack where only IPsec is needed.

### 2.4 Configuration (site-to-site VTI)

```text
crypto ipsec profile IPSEC-PROF
 set transform-set TS
 set ikev2-profile IKEV2-PROF
!
interface Tunnel0
 ip address 10.10.0.1 255.255.255.252
 tunnel source GigabitEthernet0/0
 tunnel destination 203.0.113.1
 tunnel mode ipsec ipv4
 tunnel protection ipsec profile IPSEC-PROF
```

| Command | Purpose |
|---------|---------|
| `tunnel mode ipsec ipv4` | make the tunnel an IPsec VTI |
| `tunnel protection ipsec profile` | bind the IPsec profile |
| `tunnel destination` | peer public address |
| `tunnel source` | local public interface |

- The VTI uses **`tunnel mode ipsec ipv4`** (not `gre multipoint`).

### 2.5 Key benefits

| Benefit | Detail |
|---------|--------|
| Simpler | no crypto map / ACL |
| Routing | dynamic protocols over tunnel |
| Multicast | supported |
| Scale | profile-based, dynamic |
| Resilience | failover via routing |

## 5. Exam Traps

- VTI = **route-based IPsec**; crypto map = **policy-based**.
- **`tunnel mode ipsec ipv4`** marks the tunnel as an IPsec VTI.
- **`tunnel protection ipsec profile`** binds IPsec (not a crypto map).
- Routing protocols and **multicast** run over the VTI like a normal interface.
- No interesting-traffic ACL needed — **routing triggers encryption**.

## 7. One-Minute Mental Model

Think of a **VTI** as "IPsec as an interface": give a tunnel interface an IP, point it at
the peer, and enable IPsec with `tunnel protection ipsec profile`. Whatever the routing
table sends into the tunnel (including multicast) is encrypted. No crypto map, no
interesting-traffic ACL — the **routing table is the trigger**, which is why VTI pairs so
well with dynamic routing and supersedes legacy crypto-map IPsec.
